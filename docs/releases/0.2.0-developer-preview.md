# AgentCI 0.2.0 Developer Preview

AgentCI 0.2.0 is a **pre-alpha Developer Preview / not a security certification**.

It turns the Sandbox Program's provider-neutral S0 contract into an installed, falsifiable developer workflow while preserving the rule that backend names, configuration, discovery, and missing observability are not security verdicts.

## Installed commands

```bash
agentci sandbox doctor --json
agentci sandbox verify examples/sandbox/v0alpha1-red-control-evidence.json --json --print-digest
```

`agentci sandbox doctor` performs bounded, non-destructive local readiness discovery. Default Docker, Podman, bubblewrap, WSL, and Windows Sandbox discovery/version probes do not prove a usable runtime route and cannot make those backends ready by themselves.

`agentci sandbox verify` validates one EvidenceEnvelope with the same canonical S0 validator used by repository regression tests. A **valid evidence** result means the envelope faithfully satisfies the contract, including its **recorded verdict**. It does not mean the verdict is PASS. The shipped permissive red control is intentionally valid evidence with recorded/expected verdict `FAIL`.

## Exit semantics

For `sandbox verify`:

- `0` — the EvidenceEnvelope is valid, regardless of whether its recorded verdict is `PASS`, `PARTIAL`, `UNVERIFIED`, or `FAIL`;
- `1` — the evidence is invalid, inconsistent, tampered, or cannot satisfy the canonical contract;
- `2` — usage or I/O error.

Always inspect `recorded_verdict`, `expected_verdict`, `errors`, provenance, and limitations. **Valid evidence is not a security certification.**

## What is included

- deterministic reliability/eval path: `agentci test`;
- truth-bounded sandbox readiness: `agentci sandbox doctor`;
- installed canonical S0 EvidenceEnvelope validation: `agentci sandbox verify`;
- canonical schema/TestCase and fixture attestation resources shipped from their repository-owned source files;
- accumulated fail-closed regressions for policy/authority epochs, attachment/workload binding, telemetry, network-channel semantics, authorized utility, cleanup/recovery, execution causality, backend/environment provenance, and false-PASS mutations;
- clean-wheel CI smoke from a working directory outside the repository.

## What is not claimed

- No Docker, Podman, bubblewrap, WSL, Windows Sandbox, gVisor, Kata, Firecracker, microVM, container, or other backend is certified or declared secure by AgentCI.
- Readiness is not backend execution, isolation proof, or certification.
- Fixture attestation is not provider-native attestation or production key custody.
- Behavioral outcome evidence is not automatically authority/enforcement causation evidence.
- Unknown or unavailable material evidence remains `UNVERIFIED`/non-PASS; it is not filled in by inference.
- No destructive escape testing, provider ranking, automatic privilege expansion, or cross-provider superiority claim is part of this preview.

## First-success check

From a clean wheel installation, run:

```bash
agentci sandbox doctor --json
agentci sandbox verify /path/to/v0alpha1-red-control-evidence.json --json --print-digest
```

Expected second-command semantics for the repository red control:

```text
valid=true
recorded_verdict=FAIL
expected_verdict=FAIL
certification_claim=false
```

That combination is intentional: AgentCI can validate evidence that correctly demonstrates a containment failure without converting the failure into PASS.

## Safety boundary

Use only bounded, non-destructive probes on ordinary developer and CI hosts. Do not place real secrets into fixtures/evidence or run kernel/runtime escape exploits as part of this Developer Preview. Missing capability or observability is `UNVERIFIED`, not permission to weaken the claim.
