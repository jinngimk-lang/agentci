# AgentCI Target Harness Contract v0.1

Status: **design contract**. Current released/main behavior remains authoritative until an implementation PR is independently accepted.

This contract defines the direction for executable agent targets. It is intentionally small: AgentCI evaluates targets; it does not replace the target's own application/runtime.

## Principles

1. **Real execution over simulation.** Integration claims require the real target/backend in dedicated E2E evidence.
2. **Machine-readable first.** Structured JSON is the agent/evaluator boundary; Markdown is presentation only.
3. **Inspect before execute.** A target should expose enough metadata for compatibility and safety checks before a suite runs.
4. **Fail closed.** Unknown protocol versions, malformed structured output, invalid numeric values, and exceeded limits are explicit failures.
5. **Bound resources.** Time and output are bounded; future adapters may add CPU/memory/network/filesystem isolation but must not imply a sandbox when none exists.
6. **No implicit shell interpolation.** Commands are argv arrays. User/case input is data, not shell syntax.
7. **Truthful artifacts.** Artifact references must come from the real run or be explicitly marked synthetic.
8. **Append-only trajectory evidence.** If emitted, event history is ordered evidence and must not be silently rewritten during evaluation.
9. **Progressive discovery.** Agents should be able to learn the cheap capability surface before loading detailed docs/traces.

## Compatibility with the V0 local-command contract

The active V0 work uses a minimal stdin request such as:

```json
{"id":"case-1","input":"do the task"}
```

and a minimal stdout result such as:

```json
{"success":true,"cost_usd":0.01}
```

This remains a valid legacy profile. v0.1 must be introduced without breaking fixture mode or accepted V0 target suites.

## Target manifest

A future target may declare an `agentci-target/v0.1` manifest:

```yaml
schema_version: agentci-target/v0.1
name: example-agent
transport: json-stdio-v1
command: ["python", "agent.py"]
capabilities:
  inspect: true
  trajectory: false
  artifacts: false
limits:
  timeout_seconds: 30
  stdout_bytes: 1048576
  stderr_bytes: 1048576
```

The canonical schema lives at `schemas/target-manifest.schema.json`.

### Manifest rules

- `command` is an argv array; shell strings are invalid.
- Unknown `schema_version`/`transport` values fail compatibility checks.
- Capability claims are declarations, not proof. `doctor` and E2E tests verify them.
- Limits may be tightened by an eval suite. A target cannot use the manifest to weaken a stricter suite/CI policy.

## Introspection / doctor

A future command such as:

```text
agentci target doctor <suite-or-manifest>
```

should perform cheap checks before running evals:

- manifest/schema validity;
- executable resolution;
- transport/protocol support;
- declared capability recognition;
- configured time/output bounds;
- optional handshake/health probe when safe;
- clear distinction between `compatible`, `incompatible`, and `unverified`.

It must support machine-readable output. A successful `doctor` result does **not** prove task correctness; it only establishes harness compatibility/readiness.

## Versioned request envelope

After negotiation, a richer request may use:

```json
{
  "protocol":"agentci-json-stdio/v0.1",
  "run_id":"run-uuid",
  "case":{"id":"case-1","input":"do the task"},
  "context":{}
}
```

Rules:

- `run_id` is generated by AgentCI.
- `case.id` is evidence identity, not a filesystem path.
- `context` is optional and must never implicitly contain repository credentials/secrets.
- Unsupported fields may be ignored only when the protocol explicitly allows forward compatibility; unsupported protocol versions fail closed.

## Result envelope

A v0.1 result may be:

```json
{
  "protocol":"agentci-json-stdio/v0.1",
  "success":true,
  "cost_usd":0.01,
  "output":{"summary":"done"},
  "trajectory_path":"artifacts/trajectory.jsonl",
  "artifacts":[{"path":"artifacts/result.json","media_type":"application/json"}]
}
```

Only `success` is universally required. Optional fields must be validated when present.

### Result rules

- Numeric evidence must be finite and within documented ranges.
- Paths are references, not trusted proof; AgentCI verifies allowed location/existence when it consumes them.
- A target cannot declare a result successful after exceeding a process/resource boundary.
- Human-readable stdout noise must not be mixed with a single-object JSON transport. Diagnostics belong on bounded stderr or in explicit structured fields.

## Trajectory/event evidence

Optional trajectory output uses JSON Lines; one event per line. Canonical schema: `schemas/trajectory-event.schema.json`.

Design goals:

- append-only per run;
- monotonically increasing `seq`;
- stable `run_id` and `case_id`;
- typed event kinds such as `message`, `tool_call`, `tool_result`, `checkpoint`, `artifact`, `error`;
- bounded line/file size;
- explicit timestamps/durations when available;
- no secrets in event payloads;
- artifact references are validated separately.

AgentCI summaries should expose a cheap trajectory summary (event count, latest sequence, tool/error counts) so routine inspection does not require reading the entire trace.

## Installed-command E2E requirement

Adapter acceptance must include an E2E path that tests AgentCI as a user would:

1. Install the package/entry point in a clean environment.
2. Change to an unrelated temporary working directory.
3. Resolve and invoke `agentci` from PATH rather than importing internal modules.
4. Invoke a real executable target fixture through the supported public configuration.
5. Verify exit status **and** generated JSON/Markdown evidence.
6. For adapters that depend on external software/services, run a dedicated true-backend job that fails clearly when its required dependency is absent rather than silently claiming integration coverage.

Unit tests may remain synthetic; integration claims may not.

## Inspect → execute → verify pattern

Where a target exposes meaningful state, eval scenarios should prefer:

```text
inspect precondition
→ execute target action
→ inspect/collect result
→ verify observable outcome
```

A process exit code or model self-report alone is not sufficient when an external observable result is available.

## Error taxonomy

At minimum distinguish:

- configuration error;
- compatibility/protocol error;
- executable unavailable;
- timeout;
- output limit exceeded;
- process non-zero exit;
- malformed/non-UTF-8 transport;
- invalid result schema;
- trajectory/artifact validation error;
- assertion/eval failure.

This taxonomy is part of evidence quality: agents need unambiguous errors to self-correct and regressions need stable categories.

## Security boundary

A local executable target is **not a sandbox**. `shell=False`, timeouts, process-tree cleanup, and output bounds reduce risk but do not constrain filesystem, network, CPU, memory, or syscalls in general. Documentation and reports must preserve that distinction.

## Non-goals for v0.1

- generic GUI automation;
- visual preview infrastructure;
- MCP gateway implementation;
- remote execution service;
- arbitrary plugin registry;
- complete OS sandboxing.

Those require separate evidence and design decisions.
